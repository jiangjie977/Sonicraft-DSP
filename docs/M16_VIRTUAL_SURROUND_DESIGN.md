# M16 虚拟环绕（Virtual Surround）设计方案

> 2026-11-15 立项。目标：把立体声内容渲染成「耳机里的多声道空间感」，参数全程可控，
> 默认使用零外部数据依赖的参数化模型。

本文件面向公开仓库读者，描述**设计意图、信号链、参数契约与数据格式**。
实现进度见文末「路线图」。

---

## 1. 目标与边界

### 1.1 目标

| 场景 | 期望 |
|---|---|
| 音乐 | 声场从「头中」移到「头外」，左右展开，人声仍在正前 |
| 影视 | 后方有可辨的方向性成分，对白清晰不糊 |
| 游戏 | 能分辨左后 / 右后，延迟可接受（不追求极低延迟） |

### 1.2 非目标（当前阶段不做）

- **真实多声道解码**：本项目的音频来源是系统回环，通常只有立体声；
  因此 7 声道是「上混得到的虚拟布局」，不是解码真实 5.1/7.1 内容。
- **头部追踪**：需要姿态传感器与稳定的 Fusion，列为后续阶段（参数已预留）。
- **外放串扰消除**：与耳机双耳是两套算法，后续单独评估。

## 2. 在信号链中的位置

```
系统回环捕获（立体声）
      │
      ▼
参数均衡 PEQ ──► AutoEq 耳机校正 ──► 【虚拟环绕】──► 低频管家 ──► 压限 / 限幅 ──► 输出
```

**为什么放在这里**：

- 必须在 **AutoEq 之后**：空间化会重塑频响，若放在校正之前，耳机校正曲线会被渲染染色抵消；
- 必须在 **动态处理之前**：空间化改变峰值与响度，交给后面的限幅器收口更安全；
- 与「低频管家」相邻但不重叠：低频分工由低频管家负责，本模块只做 120 Hz 以下归入 LFE 的分流。

---

## 3. 处理链（四级）

| 级 | 职责 | 关键点 |
|---|---|---|
| **① 解码** | 立体声 → 7 声道（FL/FR/C/SL/SR/CS/LFE） | M/S 分解 + 相干度分析 + 非对称 steering；120 Hz 以下并入 LFE；后中置由环绕成分提取（5 ms 延迟 + 一阶全通） |
| **② 编解码往返**（可选） | 7 声道 → Lt/Rt → 7 声道 | 强度 0 = 完全直通；默认取保守值，避免矩阵往返带来的相位损失 |
| **③ 后处理** | 逐声道 trim / 静音、中置三态、人声清晰度、低音谐波、后中置延迟 | 全部参数一阶平滑，切换不爆音 |
| **④ 渲染** | 7 声道 → 双耳；可选房间卷积 | HRTF（参数化模型 / 用户数据集）+ 早期反射 + 房间 RIR |

### 3.1 steering 规则（解码级）

以 L/R 能量差与「中置/环绕」相干度驱动声道增益：

- 声源偏左：FL 向中置方向靠，SL 更靠后；
- 声源偏右：FR 向中置方向靠，SR 更靠后；
- **范围限制**：音乐模式 ±0.8、电影模式 ±1.2 —— 避免过度 steering 造成声像跳变。

### 3.2 中置三态（后处理级）

| 状态 | 行为 |
|---|---|
| 0 关闭 | 中置静音（中置人声不输出） |
| 1 直通 | 中置人声走 C 声道（默认） |
| 2 混合 | 中置按 −3 dB 混入 FL/FR（适合耳机单点聆听） |

## 4. 声道布局与方位

| 声道 | 方位角 | 说明 |
|---|---|---|
| FL | −30° | 前置左 |
| FR | +30° | 前置右 |
| C | 0° | 中置（对白/主唱） |
| SL | −110° | 环绕左 |
| SR | +110° | 环绕右 |
| CS | 180° | 后中置（可选，延迟 + 全通增强后方定位） |
| LFE | — | 不做 HRTF，低通后按增益直接混入双耳 |

方位角定义：**0° = 正前，顺时针为正**（与 HRTF 数据集保持一致）。

---

## 5. HRTF 策略

### 5.1 默认：参数化模型（零数据依赖）

- 基于 Woodworth 近似计算 **ITD**（耳间时间差），并随方位平滑过渡到后方；
- **ILD**（耳间强度差）按方位与频率分布建模；
- 耳廓 / 肩部 / 躯干用简化滤波近似；
- 计算量低、无任何外部数据、无授权问题，适合移动端默认开启。

**已知局限**：主要建模水平面，垂直定位依靠「>3 kHz 频段向"上方"虚拟声源重定向」近似，
抬头 / 低头的听感变化不明显。

### 5.2 可选：用户自备 HRIR 数据集

模块提供导入接口，用户可放入自己测量或获授权的数据集（应用私有目录，不上传）。

**目录结构**

```
files/hrirs/<数据集名>/
├── meta.json
├── l.bin        左耳所有方位串联（float32 小端）
└── r.bin        右耳所有方位串联（float32 小端）
```

**meta.json 字段**

| 字段 | 类型 | 说明 |
|---|---|---|
| `name` | string | 显示名（重名时拒绝导入） |
| `sampleRate` | int | 必须与引擎采样率一致 |
| `taps` | int | 每个方位的抽头数（≤ 1024） |
| `azimuths` | float[] | 方位角列表，升序 |
| `elevations` | float[] | 仰角列表（当前只支持 0°） |
| `layout` | string | 目前固定 `azimuth_major`：先按方位，再按耳 |

**校验规则（导入时逐条检查，失败必须给出具体原因）**

1. 采样率与引擎不一致 → 拒绝（并提示需要的采样率）；
2. 方位数 < 8，或未覆盖 ±180° → 拒绝（无法支撑 7 声道渲染）；
3. 单文件 > 4 MB 或 `taps` 超限 → 拒绝；
4. 与已有数据集重名 → 拒绝（不静默覆盖）；
5. 文件长度与 `方位数 × taps × 4` 不符 → 拒绝。

**为什么不在应用内自带测量数据**：公开测量集的授权条款多为「仅学术 / 非商用」，
随应用分发会把授权责任转嫁给使用者；因此默认只带参数化模型，数据由用户自备。

## 7. 实时性与性能

### 7.1 实时性契约

- `Prepare()` 只在非实时线程调用，允许分配内存与预计算；
- `Process()` 内**不分配、不加锁、不打日志**，全部就地处理；
- 参数经单生产者队列投递，节点内做一阶平滑；
- 开关使用约 20 ms 交叉淡化，杜绝爆音；
- 输入含 NaN/Inf 时按 0 处理并计数，不扩散到下游。

### 7.2 性能预算（估算，待实测为准）

| 配置 | 相对开销 |
|---|---|
| 参数化 HRTF + 关闭房间 | 约 +3~5% |
| 用户数据集 HRTF（7 声道 × 2 耳） | 约 +8~12% |
| 开启房间卷积（最长 2.5 s IR） | 约 +3% |

### 7.3 延迟与内存

- 时域渲染（解码/HRTF/后处理）本身**不增加稳定延迟**；
- 房间卷积按块处理，会引入一个处理块（与会话缓冲同量级）；
- 内存：7 声道工作缓冲 + 房间 IR（0.3 s ≈ 14.4 k 点；2.5 s ≈ 120 k 点）。

## 8. 与现有架构的衔接

| 环节 | 做法 |
|---|---|
| DSP 节点 | 新增 `virtual_surround` 节点，索引由跨语言常量统一，装配时自检（错位即报错，不静默） |
| 参数下发 | 复用现有 `SetParam(node, id, value)` 通道；Kotlin 侧 `VS_*` 常量与 C++ `vs::Param` 一一对应 |
| 状态持久化 | `vs_*` 键；与均衡器 / AutoEq 一致，纳入**设备配置快照**（换设备按设备恢复） |
| 界面 | 音效库新增卡片 + 详情页三组：基础（开关/强度/中置）、HRTF（模型/方位/高度）、房间（预设/湿干比） |
| 预设 | 场景预设（音乐/电影/游戏）只改参数，不改算法 |

## 9. 已知限制

1. **上混 ≠ 真多声道**：后方成分由立体声推导，内容本身没有后方信息时效果有限；
2. **干声重的素材**（人声为主、混响很少）环绕感明显弱于影视/现场素材；
3. **参数化模型垂直定位弱**，只有用户导入含仰角的数据集才能改善；
4. **房间卷积是整体湿声叠加**，不是逐声道空间化，房间感会略微模糊前后分离；
5. 性能数字为估算，需在目标机型上实测后更新本文。

## 11. 术语表

| 术语 | 含义 |
|---|---|
| **ITD / ILD** | 耳间时间差 / 耳间强度差，人耳判断水平方位的两个主要线索 |
| **HRTF / HRIR** | 头相关传递函数 / 其脉冲响应；把某方位的声源渲染到双耳所需的滤波器 |
| **RIR** | 房间脉冲响应，用于卷积混响 |
| **steering** | 按输入能量分布动态调整各声道增益，使声像位置连续 |
| **Lt/Rt** | 立体声兼容的矩阵编解码格式（左右总分），用于可选的空间增强再解码 |
| **LFE** | 低频效果声道（.1） |

## 12. 隐私

- 本模块不访问网络（应用未声明 `INTERNET` 权限）；
- 用户导入的 HRIR 数据集仅存放于应用私有目录，不读取、不上传其他文件；
- 所有处理在本机实时完成，不落盘、不采集内容。
